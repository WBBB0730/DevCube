# symlinks

**符号链接适配**

## Problem Statement

DevCube 各处对符号链接的处理既不完整也不一致：

- **Files Tab** 的文件树把指向文件夹的链接显示成文件，点开报「不能打开目录」；树上看不出哪些条目是链接，目标不存在的链接（断链）和普通文件一模一样，点开只有一串底层错误。
- 树顶筛选与 **Content Search** 跳过所有链接，链接后面的文件既筛不出也搜不到，和树上展开能看到的对不上。
- **Project** 的路径经过链接时（如 macOS 的 `/tmp`，或自建的指向外置盘的文件夹），文件树与 **Git Tab** 收不到文件变化；链接文件夹里的变化也收不到。
- 文件与链接互相替换后，**未提交更改**和提交详情里都看不到这条变化；从 Git Tab 打开一个指向文件夹的链接（双击文件行、diff 顶栏的「打开文件」），Files Tab 报「不能打开目录」；编辑器行号栏对链接文件拿链接里写的路径去比目标文件的内容，整篇标成改动。
- 服务器上的文件树会按目标类型展开链接，本机的不会；删除一个指向文件夹的链接时，确认框说要删除「其中的全部内容」，实际只删链接；直接选中一个本机的文件夹链接上传，什么都不传，也没有提示；点开还没提交的文件夹链接的 diff 会报错。

## Solution

对齐 VS Code、JetBrains、Zed 的共同口径：**查看、打开、搜索、监听时顺着链接找到目标；删除、重命名、移动、复制、压缩时只动链接本身。**

- 链接按目标类型显示，指向文件夹的可以展开；名称后带一个小标记区分链接与断链，悬停显示指向哪里。断链照常列出，点开提示链接目标不存在。
- 筛选与 Content Search 顺着链接走；遇到断链、循环链接不报错。
- 项目路径经过链接时照常收到变化；展开过的、指向项目以外的链接文件夹也另行监听。
- Git 沿用 git 自身的语义：文件与链接互换显示为「修改」；链接文件不显示行号栏条纹。

## User Stories

1. 作为开发者，我想在文件树里展开指向文件夹的链接，以便像普通文件夹一样浏览它的内容。
2. 作为开发者，我想一眼看出哪些条目是链接，以便知道删除、移动时动的是链接本身。
3. 作为开发者，我想悬停在链接上看到它指向哪里，以便不用去终端里 `ls -l`。
4. 作为开发者，我想断链照常出现在树上并有不同的标记，以便发现并处理坏掉的链接。
5. 作为开发者，我想点开断链时看到「链接目标不存在」，以便明白为什么打不开。
6. 作为开发者，我想删除链接时确认框说清删的是链接，以便不担心连带删掉目标里的内容。
7. 作为开发者，我想「全部展开」不钻进链接文件夹，以便循环链接或指向巨大目录的链接不会把树撑爆。
8. 作为开发者，我想树顶筛选能筛出链接后面的文件和链接本身，以便树上能看到的都能筛到。
9. 作为开发者，我想 Content Search 能搜到链接后面的文件内容，以便搜索范围和树上看到的一致。
10. 作为开发者，我想项目里有断链或循环链接时筛选和搜索照常工作，以便不因一个坏链接整次失败。
11. 作为开发者，我想项目路径经过链接时文件树和 Git Tab 照常自动刷新，以便不用手动刷新。
12. 作为开发者，我想展开着的链接文件夹（哪怕指向项目以外）里有变化时树自动更新，以便看到的不是旧内容。
13. 作为开发者，我想把文件换成链接（或反过来）之后在未提交更改里看到这条变化，以便提交前不漏掉它。
14. 作为开发者，我想这条变化的 diff 能正常显示旧内容与新内容，以便看出它从什么变成了什么。
15. 作为开发者，我想链接文件在编辑器里不显示行号栏条纹，以便不被整篇误标的改动干扰。
16. 作为开发者，我想点开还没提交的文件夹链接时看到一句说明而不是报错，以便知道这里本就没有差异可看。
17. 作为开发者，我想直接选中一个文件夹链接上传到服务器时传上它指向的内容，以便和下载时一样，不会什么都没传还没有提示。
18. 作为开发者，我想服务器上的文件树与本机用同一套链接标记，以便两边的认知一致。
19. 作为开发者，我想点链接名称后的箭头、或在右键菜单里选「转到链接目标」，就打开它指向的文件、或展开并定位它指向的文件夹，以便在项目里直接看到真身。
20. 作为开发者，我想从 Git Tab 打开一个指向文件夹的链接时，Files Tab 在树里展开并定位它，以便不再看到「不能打开目录」。

## Implementation Decisions

- **列目录**：类型仍随列目录一并取回（WSL 里逐项查询太慢的约束不变），只对链接再查一次目标：取目标类型决定能否展开，取目标的真实路径作为「指向」；查不到目标即断链，「指向」取链接里写的原文。根经过链接时（如 `/tmp` → `/private/tmp`），落在根的真实路径下的「指向」换回根的写法，与树上的路径一致。条目带上链接信息（指向、是否断链）。服务器上同样处理（SFTP 的 stat / realpath / readlink）。
- **树**：链接行在名称后放一个 12px muted 标记——正常链接 `ArrowUpRight`、断链 `Link2Off`；整行悬停显示「指向 <路径>」，断链为「指向 <原文>（不存在）」。指向文件夹的链接用文件夹行；断链用文件行。「全部展开」不进入链接文件夹，链接文件夹只能手动展开（循环链接一层层展开不会卡住）。
- **转到链接目标**：链接没断、目标在树的根下（不含根自身）时，名称后的箭头可点（悬停「转到链接目标」，hover 只改字色，不触发行的单击 / 双击），右键菜单在新建组后另有一组「转到链接目标」（`ArrowUpRight`，只选一个时）；两处同一条规则、同一个动作，同「前往路径」：目标是文件夹即展开并定位，是文件即打开（焦点先交给文件树，文本文件打开后进编辑器）。目标在根外、断链时箭头只是标记，菜单里也没有这一项。本机与服务器同；筛选状态下没有链接标记，也就没有这一项。
- **打开断链**：报「链接目标不存在」。
- **从别处打开文件夹**：Files Tab 接收别处（Git Tab、Content Search）要打开的路径时先查一次条目信息，是文件夹即同「前往路径」展开并定位，是文件照旧打开（同 JetBrains 的导航：文件夹转到项目视图里选中；VS Code 只给提示与「Reveal Folder」按钮）。判断放在这一个入口，所有从别处打开的地方一并生效；Git Tab 的「打开文件」（文件行菜单、双击、diff 顶栏）随之统一为只排除已删除，未跟踪目录整体条目也能打开（悬停「无法查看差异（这是一个未跟踪目录），双击在文件树中显示」）。为此本机补上与服务器 `serverFilesStat` 同形的 `filesStat`，Files 的后端抽象多一个 `stat`；条目信息的类型改为本机与服务器共用。
- **移动 / 复制进自己里面**：经链接把文件夹移动或复制进它自己里面（如把 `real` 拖进指向 `real` 的链接文件夹），路径上看不出来：再按真实路径判一次，报与平时相同的「不能移到它自己里面」「不能复制到它自己里面」，不让系统的原始报错露出来；服务器上的移动同样处理。移动、复制的是链接本身时不算。
- **删除确认**：只选一个链接时标题为「删除符号链接 “名称”？」；服务器上与 WSL 里的后果说明，链接不算「及其中的全部内容」。
- **筛选与 Content Search**：rg 加 `--follow`（VS Code `search.followSymlinks` 默认开启的同款），并带 `--no-messages`：读文件类错误（断链、循环、无权限）不再输出，stderr 只剩查询本身的错误。文件名索引不因退出码 2 失败；Content Search 只在退出码 2 且 stderr 有内容时报错。指向项目内的链接会让同一文件出现两次，不去重（同 VS Code、JetBrains）。筛选结果由文件名单拼出，名单里看不出哪些是链接，筛选状态下的树不带链接标记（逐个检查会拖慢每次筛选，WSL 里更慢）。
- **监听**：订阅前取根的真实路径，事件路径落在真实路径下的换回登记时的路径（macOS 的 FSEvents 报回真实路径）。列目录时，若该目录的真实路径不在任何已监听的范围内（经链接进到项目以外），为它另起一路递归监听，只驱动文件通道（文件树重读与文件名索引作废），随项目监听或 Preview Window 的根监听一起释放。指向项目内的链接文件夹不需要另起：目标处的变化本就触发整树重读。指向自己上级的链接（链接所在的文件夹就在目标里，即循环链接，同 JetBrains 的判定）也不另起，否则展开它就会把整个上级目录乃至家目录都监听起来。WSL 里的目录不做这两件事。
- **Git**：name-status / numstat 的 `--diff-filter` 加上 `T`（类型变化），解析为 `M`，未提交更改、提交详情、比较都随之列出。类型变化的单文件 diff 由 git 输出成两段（删掉旧类型、新增新类型），渲染端按 `diff --git` 段拆开、以多段形式交给 diff 库（库的正式输入就是多段列表），显示为旧行全删、新行全增。工作区里未跟踪的、指向文件夹的链接，`git diff --no-index` 会顺着它当文件夹读而报错：不调 git，diff 区显示「这是一个指向目录的未跟踪符号链接，没有差异可查看」（同未跟踪目录的一句说明）。
- **行号栏条纹**：工作区里是链接的文件不取基线，不显示条纹（同 VS Code、Zed）。
- **上传直接选中的文件夹链接**：按目标的内容上传，与下载时直接选中的文件夹链接对称（同 FileZilla）；文件夹里面的文件夹链接仍跳过，免得绕圈。
- **不变**：保存写进目标、链接保留；删除、重命名、移动只动链接；本机复制保留链接；压缩存链接本身；服务器传输时文件链接传内容、文件夹里面的文件夹链接跳过（同 WinSCP 默认）；指向项目以外的链接照常可看可改，越界仍按链接路径判断。

## Testing Decisions

- 主进程用临时目录造出文件链接、文件夹链接、断链、循环链接（Windows 上跳过）：列目录的类型、指向与断链，打开断链的报错；文件名索引与 Content Search 能列出、搜到链接后面的文件（含指向项目以外的），遇到断链与循环照常完成，查询本身的错误照常报出；经链接路径订阅目录时，事件路径换回订阅时的路径；另起的链接监听只为监听范围以外的目录起、释放后不再通知。
- Git 的读取编排沿用不测的约定（见 git-data 测试头注释）：命令参数构造器断言带上 `T`；纯函数单测 name-status 的 `T` 解析为修改、单文件 diff 的拆段。未跟踪文件夹链接的判定与上传清点属读取编排，同样不测。
- 渲染端纯函数：拍平的行带出链接指向；目录比较认出链接指向与断链的变化。

## Out of Scope

- **WSL Project** 里的链接：列目录与其他项目同一套处理，但 Windows 一侧经文件共享看 Linux 链接的效果未实测（绝对路径的目标可能解析不了）；监听的两项改动不覆盖 WSL。
- 同一文件夹经两条不同路径登记成两个 Project。
- Windows 上 `core.symlinks=false` 时链接被检出成普通文件。
- 服务器传输的链接策略调整（重建链接、按传输范围判断）。
- 筛选状态下的链接标记。

## Further Notes

- 竞品调研（2026-10）：VS Code、JetBrains、Zed 都按目标类型显示、可展开、写入顺着链接、删除只删链接；搜索 VS Code 与 JetBrains 默认跟随；监听 VS Code 默认不跟随链接文件夹，JetBrains 与 Zed 会跟随。Git 客户端普遍把类型变化当难点：Sourcetree、GitKraken 都修过它不显示，GitHub Desktop、Fork 有 diff 显示不全的问题。
