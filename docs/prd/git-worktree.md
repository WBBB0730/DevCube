## Problem Statement

我经常需要在同一个仓库里并行做几件事（自己改一个分支、让 Claude Code 在另一个分支上跑），git worktree 正是为此设计的：同一仓库多份检出，互不踩文件。但 DevCube 对工作树一无所知——把工作树目录加成项目后，在外面切分支、提交图谱不会动；主项目的图谱看不出哪些分支已经被别的工作树占用，双击检出只得到一句 git 报错；也没有任何地方能看到「这个仓库还有哪些工作树、各在什么分支」，更没法在 DevCube 里新建或删除工作树。

## Solution

把工作树当成 DevCube 已有的东西来支持：**一个工作树目录就是一个 Project**（ADR-0028）。Git Tab 工具栏加一个「工作树」入口列出同仓库的全部工作树，点一下就前往对应项目（没登记的先登记）；图谱里被其他工作树检出的分支打上标记，检出它时改为引导前往那个项目；链接工作树登记为项目后，图谱能跟上外部的切分支与提交。管理面：从工作树入口、分支标签或提交右键新建工作树（建好即登记为项目并切过去），从工作树入口删除工作树（脏则追问强制，已登记的项目一并移除）与清理失效登记；存放目录在仓库设置里改，默认与 VS Code / GitLens 同为仓库旁的 `<主项目名>.worktrees/`。

## User Stories

1. 作为开发者，我想把一个链接工作树目录直接加成项目，它的 Git Tab、Files Tab、运行配置、终端都照常工作，这样工作树和普通项目没有区别。
2. 作为开发者，我在工作树项目里用终端切分支、提交后，希望它的图谱和 Tab 标签上的分支名自动跟进，而不是停在旧状态。
3. 作为开发者，我在主项目里希望别人（另一个工作树、另一个 agent）新建或删除工作树、切换分支后，图谱上的工作树列表与分支标记自动更新。
4. 作为开发者，我想在 Git Tab 工具栏有一个工作树入口，悬停或点开就能看到当前所在的工作树名（主工作树显示「主工作树」），这样一眼知道自己在哪份检出里。
5. 作为开发者，我想点开工作树入口看到同仓库的全部工作树：名字、检出的分支或提交、目录路径，主工作树和当前项目有明确标识。
6. 作为开发者，我想点列表里的另一个工作树直接跳到它对应的项目；它还没登记时自动登记为项目再跳，这样不用手动去「添加项目」找目录。
7. 作为开发者，我想在图谱的分支标签上看出「这个分支已在某个工作树检出」，这样不会白点一次检出。
8. 作为开发者，我双击或右键检出一个已被其他工作树占用的分支时，想看到一句人话提示和「前往该项目」按钮，而不是 git 的原始 fatal。
9. 作为开发者，工作树目录已经被手动删掉（git 标为可清理）时，我希望列表里那一行置灰且不可点，而不是跳去一个不存在的项目。
10. 作为开发者，我想在左树一眼认出哪些项目是链接工作树（文件夹图标不同、悬停看到属于哪个主仓库）。
11. 作为开发者，我想从工作树入口新建工作树：选新建分支 / 检出空闲的已有分支 / 分离 HEAD，填目录名（默认取分支名），看清它会放在哪；建好自动登记为项目并切过去。
12. 作为开发者，我想右键分支标签「在新工作树中检出…」、右键远程分支「在新工作树中检出…」（新建同名本地分支）、右键提交「从此提交新建工作树…」，这样常用入口不用先开列表。
13. 作为开发者，我想新建时下拉里只出现没被任何工作树占用的分支，被占用的入口置灰并注明在哪个工作树，这样不会撞上 git 的「已在别处检出」。
14. 作为开发者，我想在仓库设置里改新工作树的存放目录，默认放在仓库旁边的 `<主项目名>.worktrees/` 下，改完能立刻看到示例路径。
15. 作为开发者，我想从列表删除一个工作树：主工作树和当前项目不可删；有未提交改动时追问是否强制；它若是已登记项目则一并移除；它有运行中的会话或终端时不删，提示我先停。
16. 作为开发者，我想一键清理目录已不存在的工作树登记，而不用去终端敲 `git worktree prune`。
17. 作为开发者，我希望 git 版本过低时得到明确提示（工作树增删要求 git ≥ 2.17），而不是命令失败的原始输出。

## Implementation Decisions

- **数据模型**：`git worktree list --porcelain` 随每次图谱加载一起取（与分支 / 远程 / 贮藏并行），解析为工作树列表：路径、HEAD、检出的本地分支（detached 为空）、是否主工作树（列表首条且非裸仓库）、是否裸仓库条目、是否可清理（目录已不存在）、是否本项目所在。解析是纯函数；「本项目所在」由 IO 层按路径标注（用户视角路径与 realpath 两个别名任一匹配即命中）。命令失败（git < 2.7 等）按空列表处理，不影响图谱其余部分。加载结果新增 `worktrees` 字段，渲染端桶同步落地。
- **分支占用**：不另外解析 `for-each-ref` 的 worktreepath 字段，直接从工作树列表推导「分支 → 检出它的其他工作树」（排除本项目自身）。共享层提供纯函数 `worktreeHoldingBranch` 与展示名 `worktreeDisplayName`（主工作树固定「主工作树」，其余取目录名）。
- **监听**：仓库根解析外再问 git 两个目录：`--git-dir`（本工作树私有）与 `--git-common-dir`（主仓库公共 gitdir，主工作树两者相同）。公共目录不在监听根内（即本项目是链接工作树）时额外订阅一条公共目录监听，只驱动 git 通道。gitdir 内白名单扩展：`worktrees`、`worktrees/<名>`（工作树增删）、任一 `worktrees/<名>/HEAD`（分支占用变化）恒为元数据；`index` 只认本工作树自己的（顶层 index 对链接工作树是主工作树的暂存区，不刷新）。`.git` 为文件（链接工作树）时不再当目录处理。分类仍是纯函数，订阅形态变化（仓库根或公共目录变化）时重建。
- **工具栏入口**：分支下拉右侧、视图选项钮之前加工作树图标钮（`FolderGit2`，同其它图标钮观感，title 带当前工作树名与路径），弹层照分支下拉（同宽、顶部筛选框按展示名 / 分支 / 路径过滤、同款列表行）；列表按 git 输出顺序，主工作树标「主工作树」、当前项打勾、行尾灰字为分支或短 hash、可清理项半透明不可点、hover 显示路径。点其他行 = 经 `addProjectByPath` 登记或聚焦（与 External Open 同一收尾）。弹层顶部一行「新建工作树…」；行悬停出尾钮：可删的行（非主、非本项目、非失效）「删除工作树…」、失效行「清理失效登记…」；三者都只打开对话框。仓库无工作树数据（旧版 git / 命令失败）时整颗隐藏。
- **图谱标记与检出拦截**：本地分支标签中被其他工作树检出的，名后附 `FolderGit2` 小图标，hover 说明工作树名与路径。双击标签与右键「检出分支」对这类分支不发 git 命令，改为打开 `branch-in-worktree` 对话框：文案说明「已在工作树 X 检出，同一分支不能同时检出到两个工作树」，主按钮「前往该项目」。菜单可见性与对话框描述仍由纯函数 `buildMenuItems` / `buildSpec` 产出，`DialogEnv` 新增 `openProject` 出口。
- **左树图标**：项目树节点由主进程在对齐监听时顺带解析 gitdir，得到 `worktreeOf`（链接工作树 → 主工作树目录，其余 null）。链接工作树项目的文件夹图标换成 `FolderGit2`，hover 说明属于哪个主工作树；主工作树本身不换。
- **新建工作树**：动作 `worktree-add`（`path` + 检出方式判别联合：`new-branch` → `worktree add -b <名> -- <路径> <起点>`；`existing-branch` → `worktree add -- <路径> <分支>`；`detached` → `worktree add --detach -- <路径> <起点>`；父目录由 git 自建）。对话框为组件级表单（同拉取 / 推送）：检出方式三选一并切换字段（新建分支名 / 空闲本地分支下拉 / 只读起点），名称默认 `worktreeNameFromBranch`（斜杠换横线，手动改过即不跟随），位置只读展示 = `resolveWorktreePath(锚点, 存放目录设置, 名称)`。三个入口只差预设：工具栏 = 起点 HEAD、新建分支留空；本地分支右键 = 检出该分支（被占用时置灰并注明工作树）；远程分支右键 = 新建同名本地分支、起点为远程 ref（git 自动设上游）；提交右键 = 起点该提交、新建分支留空。校验：目录名非空且不含分隔符、新分支名合法；目录 / 分支已存在直接呈现 git 报错。成功后 `openProject(path)` 登记并前往。
- **存放目录**：每项目 git 设置新增 `worktreeDirectory`（null = 默认 `../<主项目名>.worktrees`，与 VS Code / GitLens 一致；相对主工作树解析，也可绝对）。锚点 = 工作树列表的主工作树路径，裸仓库无主工作树时退回本项目所在工作树。路径拼装是共享层纯函数（渲染端无 path 模块：分隔符跟随锚点、归一 `.` / `..`、根不可越过）。仓库设置面板加「工作树」区：一个输入 + 示例路径预览，失焦 / 回车保存；非数据键，不触发图谱重载。
- **删除工作树**：动作 `worktree-remove`（`path`, `force`）。主进程识别 git「有改动需 --force」的报错，以结构化状态 `worktree-remove-needs-force` 返回（同 push-tag 预检的先例），渲染端追问「强制删除」后带 force 重发。删除前渲染端按目录查项目：未登记 → 直接删；已登记且空闲 → 删成功后 `removeProject`（复用左树移除项目的销毁链：会话 / 终端 / 设置 / 监听）；已登记且有运行中会话或终端 → 只提示（messageOnly），不给删除按钮。顺序恒为先 git 后移项目，避免 git 删失败却丢了项目。
- **清理失效登记**：动作 `worktree-prune` → `git worktree prune`，确认后执行，不删任何文件。
- **版本门槛**：`worktree remove` 自 git 2.17；增删统一按 2.17 gate（沿用 `checkGitVersion`），过低给中文提示不执行。

## Testing Decisions

只测纯函数、零 mock（项目既有约定）：`parseWorktreeList` 用真实 `--porcelain` 样本（主 + 链接 + detached + bare + prunable + Windows 换行）；`markCurrentWorktree` 测路径别名匹配；`worktreeHoldingBranch` / `worktreeDisplayName` / `listedWorktrees` / `worktreeAnchorPath` 测排除自身、detached、主工作树命名、裸仓库回落；`worktreeNameFromBranch` / `isValidWorktreeName` / `resolveWorktreePath` 测默认目录、相对与绝对、`..` 不越根、Windows 分隔符；`classifyGitDirRel` 新增 `worktrees/` 白名单与「index 只认自己的」两组用例，`classifyCommonDirPath` 测链接工作树盯公共目录的分类；`buildWorktreeAddArgs` 三种方式、`buildWorktreeRemoveArgs` force、`worktreeRemoveNeedsForce` 用真实 stderr；`buildMenuItems` 测被占用分支的「检出分支…」改为打开 `branch-in-worktree`、三个新建入口的预设与被占用置灰；`buildSpec` 测 `branch-in-worktree` 的「前往该项目」、`worktree-remove` 的三条分叉（未登记 / 需强制追问后移除项目 / 运行中只提示）、`worktree-prune`。先例：`src/main/git-parse.test.ts`、`src/main/git-actions.test.ts`、`src/main/project-watch-classify.test.ts`、`src/renderer/src/components/git/GitContextMenu.test.ts` / `GitDialogs.test.ts`。不写 UI / e2e 测试。

## Out of Scope

- 同一 Project 内原地切换工作树（Zed 的换窗口模式，见 ADR-0028）
- 多仓库项目一次建多个工作树；子模块
- 记录「哪些工作树是 DevCube 建的」以便自动删除——删除永远由用户显式发起
- 改名 / 移动工作树（`worktree move`）、锁定 / 解锁
- 新建后自动执行初始化命令（拷 `.env`、装依赖）
- 删除工作树时顺带删除其分支
- 基于远程分支新建前自动 fetch——直接用已加载的远程 ref，需要最新就先点刷新

## Further Notes

- 术语见 CONTEXT.md（Worktree），并注意「工作区」与「工作树」的歧义标注；取舍见 ADR-0028。
- 参考实现 vscode-git-graph 无任何工作树能力（上游 issue #668 / #670 / #790 均未落地），本功能以 Zed 的工作树实现为行为参考：命令口径（`worktree list --porcelain` / `add` / `remove`）、脏工作树追问强制、主工作树与当前项不可删。两处未照搬：Zed「新建即分离 HEAD、事后再选分支」改为在对话框里一次选好分支并用工作树列表预过滤被占用的分支；默认目录不用 Zed 的 `../worktrees/<项目名>/`，而取 VS Code 内置支持与 GitLens 共用的 `../<项目名>.worktrees/`（用户基数最大，各家 agent 工具的位置互不相同、无事实标准，位置只影响 DevCube 自己新建的工作树）。
