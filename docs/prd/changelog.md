## Problem Statement

DevCube 用 bumpp 发版、应用内检查更新，但整个流程里没有更新日志。GitHub Release 的正文是空的，顶栏更新按钮点一下就直接重启安装（便携版和开发版是直接打开网页），用户不知道这次更新会带来什么，隔了几个版本才升级的人更是一无所知。维护者也没有一个固定的地方、固定的格式来写「这一版改了什么」。

## Solution

维护者在仓库根的 `CHANGELOG.md` 里手写 **Changelog**：一个正式版本一段，只写一行一件、用户能感知到的变化；Beta 不单独写，共用同号正式版那段；不强制写。发版时这份文件被整份带进更新清单，同时 CI 把这一版那段填进 GitHub Release 正文。应用里，顶栏更新按钮和「关于」页的「立即更新」都改成先弹出同一个更新弹窗：里面列出当前版本之后、到新版本为止的各版日志，确认后才重启安装（便携 / 开发版是前往下载）。开发版顶栏另外常驻一颗绿色按钮，读工作区里的 `CHANGELOG.md` 预览这个弹窗，写完日志就能看效果。

## User Stories

1. 作为维护者，我想在仓库里一个固定的文件里手写更新日志，以便日志由人来写，而不是从提交记录里拼出来。
2. 作为维护者，我想一个正式版本写一段、标题只写正式版号，以便格式简单、一眼能看出是哪一版。
3. 作为维护者，我想每条都是「新增 / 优化 / 修复」开头的短句，同类改动合并成一条，只写改了什么、不写小标题与实现细节，以便日志简洁、专业、读得懂。
4. 作为维护者，我想发 Beta 时不用再写一份，Beta 直接用同号正式版那段，以便不维护两份内容。
5. 作为维护者，我想某一版不写日志也照样能发版，以便纯内部改动（构建、测试、CI）的版本不必硬凑内容。
6. 作为维护者，我想还没定版本号时先把日志写在「未发布」这类标题下，以便边开发边记；这类标题不会出现在用户面前。
7. 作为维护者，我想发版流程不变——照常 `pnpm release`，日志自动跟着发出去，以便不多记步骤。
8. 作为维护者，我想 GitHub Release 正文自动填上这一版那段（Beta 填同号正式版那段，没写就留空），以便从网页下载的人也能看到。
9. 作为维护者，我想漏写的日志能在下一版发布前补上，以便从更早版本升上来的用户仍能看到补的内容。
10. 作为正式版用户，我想点顶栏更新按钮后先看到这次更新包含哪些改动，再决定是否重启安装，以便心里有数。
11. 作为正式版用户，我想隔了好几个版本才升级时，弹窗里列出中间每一版的日志（新的在上），以便不漏看任何一版的改动。
12. 作为 Beta 用户，我想看到的日志和正式版一致（按同号正式版挑选），以便两条线说的是同一件事。
13. 作为用户，我想没写日志的版本直接不出现，一段都没写时正文只写一句「无更新日志」，以便不被空标题打扰。
14. 作为用户，我想在「设置 → 关于」点「立即更新」时看到同一个弹窗，以便两个入口行为一致。
15. 作为可自动安装形态的用户，我想弹窗的主按钮写「重启并更新」，以便知道确认后应用会重启。
16. 作为 Windows 便携版用户，我想弹窗的主按钮写「前往下载」，确认后打开对应的 GitHub Release，以便知道这一步是去网页下载。
17. 作为用户，我想点「取消」只关掉弹窗、顶栏更新按钮仍在，以便稍后再装（更新按钮仍不可关闭、不可跳过版本）。
18. 作为用户，当还有运行中的 **Run Session** 时，我想确认「重启并更新」后仍走原有的退出确认，以便不误杀正在跑的配置。
19. 作为用户，我想弹窗里的日志支持常见 Markdown（列表、粗体、链接），链接在系统浏览器打开，以便能附上说明链接。
20. 作为用户，我想弹窗从「关于」页打开时按 Esc 先关弹窗、再按才关设置，以便分层退出。
21. 作为 **Preview Window** 里的用户，我想顶栏更新按钮的行为和主窗口一致，以便不学两套。
22. 作为开发者，我想开发版顶栏常驻一颗绿色的更新按钮，点开就是用户看到的那个更新弹窗、内容取工作区里的 `CHANGELOG.md`，以便写完日志立刻看效果。
23. 作为开发者，我想绿色按钮每次点开都重新读文件，以便改完不用重启应用。
24. 作为开发者，我想绿色按钮列出比当前版本新的全部段落，目标版本取其中最新一段，以便通过多写几段来预览多版本的排版。
25. 作为开发者，我想本地还没写新段落时，绿色按钮仍能打开弹窗（目标版本显示为当前版本 +1 补丁号，正文为「无更新日志」），以便预览「没写日志」时用户看到什么。
26. 作为开发者，我想绿色按钮的确认按钮是「前往下载」，点了打开 GitHub Releases 列表页（预览的版本尚未发布），以便行为与开发版的真实更新一致。
27. 作为开发者，我想真实更新按钮与绿色预览按钮互不影响——绿色按钮不联网，真实按钮只在 GitHub 真有新版本时出现，以便分得清看到的是哪一种。
28. 作为开发者，我想把 `package.json` 的版本号临时改低就能在开发版里走一遍真实检查，以便验证联网检查、按 **Release Edition** 过滤与挑段落的真实链路。
29. 作为用户，我不想在打包出来的正式版或 Beta 里看到绿色预览按钮，以便它只是开发工具。

## Implementation Decisions

- **日志文件与格式**：仓库根 `CHANGELOG.md`，Keep a Changelog 形态——一级标题「更新日志」，每个正式版本一个二级标题 `[X.Y.Z] - YYYY-MM-DD`（方括号与日期可省），新版本在上；段内为无序列表，写法规则：每条以「新增 / 优化 / 修复」开头的短句、句末不加句号；同类改动合并为一条；只写改了什么，不写小标题、实现细节与数值参数；内部改动（构建、测试、CI）不写。只有标题是正式版号的二级标题算版本段；「未发布」、带 prerelease 的标题等一律忽略。段正文取到下一个一 / 二级标题为止，以 Markdown 原文保存。历史补写 1.6.1～1.9.0；1.6.0 只打了 tag、发版流水线在 macOS 签名一步失败而没有生成 Release，用户实际从 1.6.1 起拿到那批改动，所以记在 1.6.1。
- **解析与挑段落（共享纯函数模块）**：用成熟的 Markdown 解析器（mdast-util-from-markdown）切段，代码块里的井号不误判；版本比较用 semver。对外接口：
  - 解析：全文 → 版本段列表 `{ version, date | null, body }`（同一版本写了多段只取第一段）。
  - 版本对应的段版本号：去掉 prerelease / build（Beta 共用同号正式版）。
  - 挑段落：给定当前版本与目标版本，两端都换成正式版号，取「当前 < 段版本 ≤ 目标」的段，新→旧。
  - 取某次发版那一段：给 CI 填 Release 正文用。
  - 本地预览：给定当前版本，取比它新的全部段（新→旧），目标版本取最新一段；一段都没有时目标为当前版本 +1 补丁号。
- **下发（ADR-0035）**：electron-builder `releaseInfo.releaseNotesFile` 指向 `CHANGELOG.md`，整份写进 `latest.yml` / `latest-mac.yml` 的 `releaseNotes`。不用 electron-updater 的 `fullChangelog`（订阅源只给最近 10 条），也不把日志作为 Release 附件另行下载。
- **主进程更新编排**：采纳 / 清空候选时，版本号与日志一起换——从候选的 `releaseNotes`（字符串时）解析并挑出当前版本之后、到候选为止的段落，放进推给渲染层的更新状态（新增字段：日志段列表）；无候选、跨线候选或旧版本清单没有日志时为空。
- **Release 正文**：CI 在 verify 阶段的发版元数据脚本里取出这一版那段（Beta 取同号正式版），作为多行输出（随机分隔符）交给发布步骤，经环境变量传给 `gh release create --notes`；没写即空正文。构建仍 `--publish never`。
- **更新弹窗（渲染层共用组件）**：沿用小对话框外壳（无标题栏、提示语 + 内容 + 底部按钮条；外壳新增宽度覆盖，弹窗 480px）。顶部两行：「{显示名} {目标版本} 可用」为标题、其下「当前版本 {当前}」为副标题；日志直接排在弹窗正文里（不套内框），限高可滚动：每段一行段头——版本号与标题同号加粗、日期靠右小字——其下 Markdown 正文按弹窗正文排紧凑列表（react-markdown + GFM，原始 HTML 不渲染，链接经系统浏览器；不套文章排版）；段与段之间只靠留白；没有段落时正文写「无更新日志」（正文样式）。按钮：「取消」+ 主按钮——可自动安装形态「重启并更新」，便携 / 开发版「前往下载」。确认后执行原有更新动作（`app.quit` → 退出确认 → 安装，或打开 Release），不改退出闸。
- **入口**：顶栏更新按钮（主窗口与 **Preview Window** 共用顶栏组件）与「关于」页「立即更新」都只负责开弹窗，各自持有弹窗开关；顶栏弹窗渲染在窗口拖拽区之外。「关于」页的 Esc 分层：先关更新弹窗，再关错误框，最后关设置。顶栏按钮的出现条件与提示文字不变。
- **开发版本地预览**：仅未包装开发——渲染层以构建期常量判定是否开发构建，顶栏在宿主动作钮之后、真实更新按钮之前常驻一颗绿色（运行按钮同色）更新图标钮，提示「预览更新日志（本地）」；点击经 IPC 让主进程读应用目录下的 `CHANGELOG.md` 并返回本地预览（含显示名与当前版本），打开同一个更新弹窗；确认打开 GitHub Releases 列表页。主进程只在未包装时注册该 IPC；打包产物既无该按钮也无该处理器。真实更新流程（ADR-0017：连 GitHub、同便携）保持不变。

## Testing Decisions

好测试：只测外部可观察的纯函数行为——给定日志全文 / 版本对，断言切出的段、挑出的段与顺序；不测 electron-updater 网络、不测真实打包与安装、不测 CI 编排。

要测的模块：

- **解析**：方括号与日期可省、「未发布」与带 prerelease 的标题被忽略、代码块里的井号不算标题、带链接定义的标题可识别、同版本多段只取第一段、空文件。
- **挑段落**：区间上下界、没写的版本跳过、Beta 两端去后缀（含同号 Beta 之间无段落）、非法版本。
- **取发版那一段**：Beta tag 取同号正式版、没写为空。
- **本地预览**：目标取最新一段、一段都没有时为当前版本 +1 补丁号（含 Beta 当前版本）。

先例：`release-edition`、`app-update` 等 shared 纯函数 vitest。

维护者手动验证：

- **看效果**：开发版点绿色按钮；想看多段就在 `CHANGELOG.md` 里多写几段比当前版本新的，或把 `package.json` 版本号改低。
- **验真实链路**：把 `package.json` 版本号改低后重启开发版，等真实检查出现更新按钮再点开（功能上线前，GitHub 上的清单没有日志，弹窗正文为「无更新日志」）。测完改回版本号。
- **打包配置**：本地打一次包，看 `dist/latest-mac.yml` 里 `releaseNotes` 是否为整份日志；发版元数据脚本可本地对当前版本 tag 直接跑。
- **重启并更新**：只能在正式签名的安装版上走；功能上线后的第一次发版先只发 Beta，在 Beta 上走通再发正式版。

## Out of Scope

- 从 git 提交自动生成日志（changelogithub 等）
- 发版前强制检查日志是否已写、提醒写日志
- electron-updater 的 `fullChangelog` / 读取 Release 订阅源
- 把日志作为 Release 附件或经 REST API 另行拉取
- 本地假更新源（本地打包 + 本地服务器）与开发专用命令 / 模式开关
- 为 Beta 单独写日志；同号 Beta 之间（如 beta.1 → beta.2）的差异说明
- 「跳过此版本」、暂时隐藏更新按钮
- 更新后首次启动时弹「本次更新内容」
- 日志多语言

## Further Notes

- 决策与取舍见 ADR-0035；更新身份过滤见 ADR-0014，开发版更新策略见 ADR-0017。
- 功能上线的那一版本身，用户从旧版本升上来时看不到弹窗（旧版本没有弹窗代码）；应用内第一次出现日志是再下一次更新。补写的 1.6.1～1.9.0 在网页 Release 正文里可见，也是开发时改低版本号验证用的真实数据。
- 为本地预览在 `CHANGELOG.md` 里临时加的「未来版本」段落会随下一次发版进入更新清单，发版前删掉。
- 与 `docs/prd/in-app-update.md`（更新弹窗接管顶栏按钮与「立即更新」的点击）、`docs/prd/ci-release.md`（Release 正文不再留空）相互对应。
