# changelog

**更新日志**

## Problem Statement

DevCube 用 bumpp 发版、应用内检查更新，但整个流程里没有更新日志。GitHub Release 的正文是空的，顶栏更新按钮点一下就直接重启安装（便携版和开发版是直接打开网页），用户不知道这次更新会带来什么，隔了几个版本才升级的人更是一无所知。维护者也没有一个固定的地方、固定的格式来写「这一版改了什么」。

## Solution

维护者在仓库根的 `CHANGELOG.md` 里手写 **Changelog**：一个正式版本一段，只写一行一件、用户能感知到的变化；Beta 不单独写，共用同号正式版那段；不强制写。发版时这份文件被整份带进更新清单，同时 CI 把这一版那段填进 GitHub Release 正文。应用里，顶栏更新按钮和「关于」页的「立即更新」都改成先弹出同一个更新弹窗：里面列出当前版本之后、到新版本为止的各版日志，确认后才重启安装（便携 / 开发版是前往下载）。开发版顶栏另外常驻一颗绿色按钮，读工作区里的 `CHANGELOG.md` 预览这个弹窗，写完日志就能看效果。

## User Stories

1. 作为维护者，我想在仓库里一个固定的文件里手写更新日志，以便日志由人来写，而不是从提交记录里拼出来。
2. 作为维护者，我想一个正式版本写一段、标题只写正式版号，以便格式简单、一眼能看出是哪一版。
3. 作为维护者，我只说一句「写更新日志」，就能按固定的写法规则一次写出这一版的日志、连版本号一并定好，以便日志简洁、专业，不用再逐条调整。
4. 作为维护者，我想发 Beta 时不用再写一份，Beta 直接用同号正式版那段，以便不维护两份内容。
5. 作为维护者，我想某一版不写日志也照样能发版，以便纯内部改动（构建、测试、CI）的版本不必硬凑内容。
6. 作为维护者，我想发版流程不变——照常 `pnpm release`，日志自动跟着发出去，以便不多记步骤。
7. 作为维护者，我想 GitHub Release 正文自动填上这一版那段（Beta 填同号正式版那段，没写就留空），以便从网页下载的人也能看到。
8. 作为维护者，我想漏写的日志能在下一版发布前补上，以便从更早版本升上来的用户仍能看到补的内容。
9. 作为正式版用户，我想点顶栏更新按钮后先看到这次更新包含哪些改动，再决定是否重启安装，以便心里有数。
10. 作为正式版用户，我想隔了好几个版本才升级时，弹窗里列出中间每一版的日志，以便不漏看任何一版的改动。
11. 作为 Beta 用户，我想看到的日志和正式版一致（按同号正式版挑选），以便两条线说的是同一件事。
12. 作为用户，我想没写日志的版本直接不出现、一段都没写时只有一句提示，以便不被空标题打扰。
13. 作为用户，我想在「设置 → 关于」点「立即更新」时看到同一个弹窗，以便两个入口行为一致。
14. 作为可自动安装形态的用户，我想弹窗的主按钮写「重启并更新」，以便知道确认后应用会重启。
15. 作为 Windows 便携版用户，我想弹窗的主按钮写「前往下载」，确认后打开对应的 GitHub Release，以便知道这一步是去网页下载。
16. 作为用户，我想点「取消」只关掉弹窗、顶栏更新按钮仍在，以便稍后再装。
17. 作为用户，当还有运行中的 **Run Session** 时，我想确认「重启并更新」后仍走原有的退出确认，以便不误杀正在跑的配置。
18. 作为用户，我想弹窗里的日志支持常见 Markdown、链接在系统浏览器打开，以便能附上说明链接。
19. 作为用户，我想从「关于」页打开的弹窗按 Esc 先关弹窗、再按才关设置，以便分层退出。
20. 作为 **Preview Window** 里的用户，我想顶栏更新按钮的行为和主窗口一致，以便不学两套。
21. 作为开发者，我想开发版顶栏常驻一颗绿色的更新按钮，点开就是用户看到的那个更新弹窗、内容取工作区里的 `CHANGELOG.md`，以便写完日志立刻看效果。
22. 作为开发者，我想绿色按钮每次点开都重新读文件，以便改完不用重启应用。
23. 作为开发者，我想绿色按钮列出比当前版本新的全部段落，以便通过多写几段来预览多版本的排版。
24. 作为开发者，我想本地还没写新段落时，绿色按钮仍能打开弹窗，以便预览「没写日志」时用户看到什么。
25. 作为开发者，我想绿色按钮的确认按钮与开发版的真实更新一致，是「前往下载」，以便行为一致。
26. 作为开发者，我想真实更新按钮与绿色预览按钮互不影响——绿色按钮不联网，真实按钮只在 GitHub 真有新版本时出现，以便分得清看到的是哪一种。
27. 作为开发者，我想把 `package.json` 的版本号临时改低就能在开发版里走一遍真实检查，以便验证联网检查、按 **Release Edition** 过滤与挑段落的真实链路。
28. 作为用户，我不想在打包出来的正式版或 Beta 里看到绿色预览按钮，以便它只是开发工具。

## Implementation Decisions

- **日志文件与格式**：仓库根 `CHANGELOG.md`，Keep a Changelog 形态——一级标题「更新日志」，每个正式版本一个二级标题 `[X.Y.Z] - YYYY-MM-DD`（方括号与日期可省），新版本在上；段内为无序列表，写法见「写法规则」；写了就要有版本号，还没发版也直接写下一个版本号的段落。只有标题是正式版号的二级标题算版本段，其余二级标题（如带 prerelease 的）一律忽略。段正文取到下一个一 / 二级标题为止，以 Markdown 原文保存。1.6.0 没有生成 Release（发版流水线在 macOS 签名一步失败），用户从 1.6.1 起才拿到那批改动，所以记在 1.6.1。
- **写法规则**：维护者只说「写更新日志」时，照以下规则一次写完：版本号与各项取舍自行决定，不停下来确认，取舍在回复里说明；只改 `CHANGELOG.md`，不提交。
  - 范围：以上一个正式版标签到当前的最终差异为准，只写用户能感知到的变化；同一版本周期内引入又改掉的不写。
  - 版本号：有大功能升次版本号，其余升补丁号；标题写 `[X.Y.Z]`，不写日期；这一版已有段落时就地改写。
  - 条目：每条一句，以「新增 / 优化 / 修复」开头，句末不加句号，按新增、优化、修复排列；一个功能一条，同一功能的多处改动合并。
  - 粒度：只写功能层面的概括——新增与优化都只写功能名，不写「支持……」之类的展开，不列改进的方面与具体做法；修复写一个概括的问题现象，即「修复……的问题」，不罗列多个现象。
  - 强调：每版最重要的一条整条加粗，最多一条；没有突出的就不加粗。
  - 细小改动：不影响功能（功能照样能用、结果不出错、不丢数据）的，即使是缺陷修复，也不单独成条，统一归为一条「优化交互体验」，放在优化类最后；影响功能的，再小也单独写。
  - 内部改动（重构、依赖、构建、测试、CI、文档）不写；带来用户能感知的变化时，按变化写。
  - 用词以 `CONTEXT.md` 为准，不照搬提交标题。
- **解析与挑段落（共享纯函数模块）**：更新编排、开发版预览与发版脚本共用一处实现；用成熟的 Markdown 解析器切段（代码块里的井号不误判），版本比较用 semver。同一版本写了多段只取第一段；版本对应的段去掉 prerelease / build（Beta 共用同号正式版）。更新时两端都换成正式版号，取「当前 < 段版本 ≤ 目标」的段，新→旧；发版时取这一版那段；本地预览取比当前版本新的全部段，目标版本取最新一段，一段都没有时为当前版本 +1 补丁号。
- **下发（ADR-0035）**：electron-builder `releaseInfo.releaseNotesFile` 指向 `CHANGELOG.md`，整份写进 `latest.yml` / `latest-mac.yml` 的 `releaseNotes`。不用 electron-updater 的 `fullChangelog`（订阅源只给最近 10 条），也不把日志作为 Release 附件另行下载。
- **主进程更新编排**：日志随候选一起换——采纳候选时从其 `releaseNotes` 挑出当前版本之后、到候选为止的各段，随更新状态推给渲染层；无候选、跨线候选或旧版本清单没有日志时为空。
- **Release 正文**：CI 发版时取这一版那段作正文（Beta 取同号正式版），没写即空正文。构建仍 `--publish never`。
- **更新弹窗（渲染层共用组件）**：标题「{显示名} {目标版本} 可用」、副标题「当前版本 {当前}」，其下新→旧列出各段（段头为版本号与日期，正文用 react-markdown + GFM 渲染，原始 HTML 不渲染，链接经系统浏览器）；没有段落时正文写「无更新日志」。按钮：「取消」+ 主按钮——可自动安装形态「重启并更新」，便携 / 开发版「前往下载」。确认后执行原有更新动作（`app.quit` → 退出确认 → 安装，或打开 Release），不改退出闸。
- **入口**：顶栏更新按钮（主窗口与 **Preview Window** 共用顶栏组件）与「关于」页「立即更新」都只负责开弹窗。「关于」页的 Esc 分层：先关错误框，再关更新弹窗，最后关设置。
- **开发版本地预览**：仅未包装开发——顶栏常驻一颗绿色（运行按钮同色）更新图标钮，提示「预览更新日志（本地）」；点击时主进程读工作区的 `CHANGELOG.md`，按本地预览规则打开同一个更新弹窗；确认打开 GitHub Releases 列表页（预览的版本尚未发布）。主进程只在未包装时注册该处理，打包产物既无该按钮也无该处理器。真实更新流程（ADR-0017：连 GitHub、同便携）保持不变。

## Testing Decisions

好测试：只测外部可观察的纯函数行为——给定日志全文 / 版本对，断言切出的段、挑出的段与顺序；不测 electron-updater 网络、不测真实打包与安装、不测 CI 编排。

要测的模块：

- **解析**：方括号与日期可省、非版本号与带 prerelease 的标题被忽略、代码块里的井号不算标题、带链接定义的标题可识别、同版本多段只取第一段、空文件。
- **挑段落**：区间上下界、没写的版本跳过、Beta 两端去后缀（含同号 Beta 之间无段落）、非法版本。
- **取发版那一段**：Beta tag 取同号正式版、没写为空。
- **本地预览**：目标取最新一段、一段都没有时为当前版本 +1 补丁号（含 Beta 当前版本）。

先例：`release-edition`、`app-update` 等 shared 纯函数 vitest。

维护者手动验证：

- **看效果**：开发版点绿色按钮；想看多段就在 `CHANGELOG.md` 里多写几段比当前版本新的，或把 `package.json` 版本号改低。
- **验真实链路**：把 `package.json` 版本号改低后重启开发版，等真实检查出现更新按钮再点开。测完改回版本号。
- **打包配置**：本地打一次包，看 `dist/latest-mac.yml` 里 `releaseNotes` 是否为整份日志；发版元数据脚本可本地对当前版本 tag 直接跑。
- **重启并更新**：只能在正式签名的安装版上走。

## Out of Scope

- 从 git 提交自动生成日志（changelogithub 等）
- 发版前强制检查日志是否已写、提醒写日志
- electron-updater 的 `fullChangelog` / 读取 Release 订阅源
- 把日志作为 Release 附件或经 REST API 另行拉取
- 本地假更新源（本地打包 + 本地服务器）与开发专用命令 / 模式开关
- 为 Beta 单独写日志；同号 Beta 之间（如 beta.1 → beta.2）的差异说明
- 「跳过此版本」、暂时隐藏更新按钮
- 更新后首次启动时弹「本次更新内容」
- 日志多语言

## Further Notes
