# 服务器文件经系统 ssh 的 sftp 子系统，SFTP 客户端自己写

> 拟被 ADR-0041 取代（提案中，尚未实施）：连接改由内置的 ssh2 完成后，改用它自带的 SFTP，本文的自写客户端随之删除。

**Server** 的 **Files Tab**（`docs/prd/server-files.md`）要经系统 `ssh` 连接（ADR-0038），于是由主进程起 `ssh -s <目标> sftp`（连接目标、绕开代理直连与 askpass 同其他连接），在它的标准输入输出上跑 SFTP 协议。问题在于 Node 生态里没有一个仍在维护、又能跑在外部 `ssh` 进程上的 SFTP 客户端库。我们决定在主进程里自己写一个 SFTP v3 客户端：OpenSSH 只实现 v3（draft-ietf-secsh-filexfer-02），协议早已定型，客户端只需十余种报文（打开 / 读 / 写 / 关闭、读目录、stat / lstat、realpath、新建与删除目录、删除、改名）。

实测（`docs/prd/server-files.md` 实测记录）：约 150 行的最小实现，按 OpenSSH `sftp` 的默认流水线参数（每块 32 KB、最多 64 个未完成请求），上传、下载都跑满了带宽，与同一连接上的纯 ssh 通道和系统 `sftp` 命令持平。

## Considered Options

- **自己写 SFTP v3 客户端（选中）**：不引入依赖，也不绕开系统 `ssh`；代价是协议层由我们维护。
- **`ssh2` 的 SFTP**：Node 里最成熟的实现，但它和 `ssh2` 自己的 SSH 连接绑在一起（构造时要它的协议对象和通道信息），套在外部 `ssh` 上只能伪造内部对象，属于 hack；改用 `ssh2` 自己连接，又违背 ADR-0038。
- **`ssh2-streams` 的 `SFTPStream`**：能单独套在任意流上，但已随 `ssh2` 1.x 合并而停止维护。
- **驱动系统 `sftp` 命令（`-b` 批处理）**：要解析给人看的输出，文件名带空格、换行或特殊字符时容易出错；拿不到逐块进度，也不能并发。
- **Go 的 `pkg/sftp` 做小助手**：库成熟，也支持跑在管道上；但每个平台要多打包一个程序、构建多一套工具链，主进程与小助手之间还得再定一套通信协议。
- **在服务器上跑 shell 命令（`ls` / `cat` 等）**：依赖服务器上命令的有无和输出格式；每个操作要么新起一次 `ssh`（重新认证），要么自己设计二进制分帧。

## Consequences

- 报文编解码与分块计划（顺序出块、短读补读、读到文件尾即止）放在 shared 里，按纯函数测试；并发流水线、与 `ssh` 进程和本机文件读写的衔接在主进程。
- 只用 v3 的基本报文，不依赖 OpenSSH 扩展。改名用基本的 RENAME，目标已存在即失败，正合「重名即失败」；家目录用 realpath `.` 取得。
- 每块 32 KB（同 OpenSSH `sftp`）；同时在途的块数按往返时延自适应，至多 64 块，不做成设置。起初沿用 `sftp` 的固定 64 块（约 2 MB），但 SFTP 按序回复、发出的请求撤不回：慢线路上下载期间别的请求、取消后的下一个请求都要排在这 2 MB 之后（模拟 256 KB/s 时要等 8 秒，几十 KB/s 时约一分钟）。现在同 TCP Vegas 的思路：以见过的最短往返为不排队的基准，估出服务器那边排着的块数，保持在 1 到 2 块；一条连接一个窗口，跨传输沿用，从 1 块起步。模拟往返 40 ms 时，5 MB/s、256 KB/s、30 KB/s 三档的吞吐为 4.2 MB/s、245 KB/s、29 KB/s，下载中与取消后查一次信息分别约 60 ms、0.2 秒、1–2 秒。
- 取消即时生效：已发出的请求不等回来；出错或取消时照发关闭但不等它的回复（它排在未回来的读写之后）。
- 服务器须启用 SFTP 子系统（OpenSSH 默认启用）；没有启用时报出明确原因。
- 文件连接与 **SSH Terminal**、状态连接各是一条 `ssh`，互不复用；没记住密码时各问一次。
- Windows 上系统 OpenSSH 以管道方式启动待实测，与状态连接是同一个问题。
