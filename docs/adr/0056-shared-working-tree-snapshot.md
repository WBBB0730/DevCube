# 工作区状态按仓库共用一份，未跟踪文件不统计行数，文件树开窗渲染

一个有 4 万多个未跟踪文件的仓库（Unity 工程尚未提交的资源）把 DevCube 拖到卡死：**Files Tab** 为了给树标 Git 颜色、**Git Tab** 的**未提交更改**详情为了列文件，每次刷新都各自请求一份未提交详情；主进程为给未跟踪文件补「新增行数」，不限并发地把它们全部读了一遍（实测同时开着 8 万多个文件句柄、读进约 500 MB）；两边的请求在窗口切回、文件变化、自动获取时反复触发，前一轮没算完后一轮又来；渲染端的文件树不分可见与否全部画出，隐藏着的 Git Tab 里就有近 60 万个 DOM 节点。只跑 `git status` 时同样的仓库只要约 60 ms。

我们决定：

- **未跟踪文件不统计行数**：git 不为它们提供 numstat，列表阶段不读工作区文件，内容只在点开 diff 时取。VS Code、Zed、JetBrains、GitHub Desktop、lazygit 与参考实现 vscode-git-graph 都是这个口径。
- **工作区快照按仓库共用一份**：一次 `git status` 与一份未提交详情，**未提交更改**详情、Files Tab 的 Git 标记、图谱的未提交计数共用（同 VS Code / Zed / JetBrains 的文件树着色复用变更列表的状态）。仓库有变化即作废——推送 `git:changed` 之前、每次写动作完成后（含渲染端自刷新的静默动作）、渲染端主动刷新（手动、切回、窗口回到前台、自己的文件操作之后）时；作废后的第一次读取才重算。读取在途时，同一代的请求共用它，作废后到的请求排在它后面：同一仓库同时最多一轮在跑、一轮排队，排队那轮把之后到的请求都并进去（同 VS Code 的 Throttler、JetBrains 的 SingleTaskRunner）。读失败不留。
- **所有 git 子进程带 `GIT_OPTIONAL_LOCKS=0`**：读状态不顺手改写 index，不让自己的读取改动 `.git`、被项目监听当成变化再刷一轮，也不与用户终端里的 git 抢锁；命令本身要做的事不受影响（同 Zed 的 `--no-optional-locks`、lazygit、VS Code 的 status）。
- **Git 文件树按可见区间开窗**：只画视口内的行与它们的上级目录，其余整段换成等高占位。目录头的 sticky 约束框（目录子树）高度不变，逐级吸顶与被下一个目录顶走的效果照旧。区间由 `@tanstack/react-virtual` 算，只取区间、不接管定位；提交面板两段的开合由父组件持有，按「标题 / 内容行 / 分隔线 / 底部留白」的固定尺寸算出各段位置。

## Considered Options

- **按需补算可见行的行数**：保留展示、开销只随可见行数增长，但没有任何成熟客户端这样做，还要多一套按行异步加载与缓存失效。
- **保留补算，限制并发与数量**：改动最小，但阈值是拍脑袋的，阈值以内的文件每次刷新仍要全读一遍。
- **Files Tab 另调只跑 `git status` 的轻量接口**：改动小，但两边仍各跑各的，合并逻辑要做两遍；Files Tab 的颜色也就不再与提交面板同源。
- **改成绝对定位的常规虚拟列表**：实现常见，但嵌套 sticky 的逐级吸顶要另写一套吸顶层（VS Code 的 sticky scroll 即如此）；开窗保留原有的嵌套 DOM，吸顶交给浏览器。
- **给文件数量设上限**（VS Code 超过 1 万条截断并提示、JetBrains 未跟踪超过 1000 个不展开）：去掉读文件、文件树开窗之后实测不需要，不设。

## Consequences

- 未跟踪文件的行尾不再有「+N」（PRD git-graph「详情与 diff」随之修改）。
- 写动作、渲染端的主动刷新路径新增作废步骤；以后新增会改动工作区、又不经监听通知的路径，也要作废快照，否则在下一次监听通知前读到的是旧状态。
- 快照留在主进程内存里，直到下一次作废后被新结果替换。
- 不再顺手刷新 index：外部工具大批改动文件的修改时间后，在别的 git 命令刷新 index 之前，`git status` 会重新比对这些文件的内容。
