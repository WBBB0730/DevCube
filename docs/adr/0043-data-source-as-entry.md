# 数据源是和 Project、Server 并列的独立条目，项目里用「+」打开完整视图

用户连的库以云数据库为主，常有几个项目共用同一个库，偶尔有本地的和服务器上的。我们决定：

- 把数据库连接登记为 **Data Source**，和 **Project**、**Server** 并列在左树里。一个库通常只登记一份，几个项目共用它；也允许登记多份，添加或编辑时连接目标与已登记的重复，提交前二次确认一次，不禁止。
- **Project** 里经 Tab 栏「+」→「连接到数据源」，开一个 **Data Source Tab**。它和 Terminal、Run Session 并列，随项目保存，和 SSH Terminal 的壳一样。
- 项目里开着的 Data Source Tab，本身就代表项目和库之间的关联，不另建绑定关系。

项目里开的是完整视图，和 Data Source 自己的常驻 Tab 一模一样：右侧是目录，左侧在「当前对象」和「控制台」两格之间切换。两格各自保留内容，点一张表不会冲掉查询结果。Tab 里不再分小 Tab，这和 **Files Tab**「同一时刻只打开一个条目」是同一个取向。要同时看两张表，或开两份查询，就再开一个同库的 Tab。

「重复」只按连接目标判断（类型、地址、端口、用户名、默认库，SQLite 为文件；地址不分大小写），登记本身还带着名称、加密要求、是否直连、记住的密码、目录里显示的库（ADR-0045）和它自己的运行配置，两份登记在这些上面可以各不相同。代码里的 `DataSourceTarget` 是连接所需的全部参数：连接目标之外，网络类还带着按类型不同的加密要求与是否直连；判重（`sameDataSourceTarget`）只比其中的连接目标部分。实际也有要分开登记的时候：同一个库一份直连、一份经代理，或者加密设置不同；按用途分开，各挂各的运行配置；起不同的名称，便于区分环境。所以重复不是错，只是可疑——多半是忘了已经登记过。按工作区「可疑但允许的操作用二次确认」的惯例，提交时问一句，确认了就照样登记。**Server** 同样处理：同一台服务器可以登记多台，从 SSH 配置勾选已添加过的主机、手填或编辑成与已登记的相同时，都在提交前确认；手填目标的地址同样不分大小写。

## Considered Options

- **连接挂在 Project / Server 下（和命令型 Run Configuration 的归属规则一样）**：贴合「以项目为维度」，以后做自动发现也顺手。但云数据库不属于任何项目，多个项目共用的库也要各建一份。
- **独立条目，再和项目多对多绑定**：共用的库只存一份，项目里只列绑定了的库。但多了一层要管理的绑定关系（绑定、解绑、移除时的连带处理），而项目里开着的 Tab 已经能表达这层关联。
- **项目里只开控制台**（同 Server 的做法：项目里只开会话）：Tab 更轻。但写代码时最常做的恰恰是翻表核对数据，这样就得离开项目去左树里看，dev server 的输出也看不到了。
- **Data Source Tab 里分小 Tab**（每张表、每个控制台各占一个，同 DataGrip、TablePlus）：最灵活。但 Tab 里套着 Tab，要处理关闭和放不下时的溢出，界面上的东西会变多。
- **左侧只有一格，点表就替换查询结果**：最简单，但查询结果会被冲掉，不能接受。
- **同一个库只许登记一份**（最初的做法）：添加时命中已登记的就不新增、直接选中那一个；编辑成与别的相同时「保存」置灰。用户明明点了「添加」却没有新条目，想分开登记（不同的名称、直连设置或配置）也做不到。
- **重复时在表单里常驻提示或置灰按钮**：信息都在界面上，但表单里要多一块只在少数情况下有用的内容；二次确认只在提交那一刻出现，平时界面上什么都不多。

## Consequences

- 左树多了第三类条目；排序、Pin、拖拽、名称筛选和按类型筛选，都要能处理三类条目。
- Data Source 和 Server 之间没有关系，服务器上的库也登记成 Data Source 直接连。以后要经由服务器的 SSH 隧道连接时，再让 Data Source 引用一台已登记的 Server。
- 自动发现在这个模型下只能退一步，变成「添加时从项目里导入」：只导入一次，之后不同步。首版不做。
- 同一个库可以同时开在好几处，每个 Tab 有自己的连接和目录展开状态。
- 同一个库可以有几份登记，各自独立：各有自己的 Tab、配置、记住的密码、显示的库与表结构缓存（ADR-0045），互不同步。主进程的添加总是新增，不再按连接目标合并。
- 表数据和查询结果不能同时显示在屏幕上，要在两格之间切换。
