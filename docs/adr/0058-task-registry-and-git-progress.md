# 耗时操作经主进程的任务登记处报进度；Git 取消结束整棵进程树，拉取拆成先获取、再拉取

克隆、拉取、推送这类 **Task** 要能显示进度、隐藏到任务清单、在 Dock / 任务栏上显示进度、在退出确认里计数（`docs/prd/task-progress.md`）。原先的进度各走各的：克隆一条专用 IPC 加对话框里手写的进度条，服务器传输一条，压缩又一条，速度和剩余时间都没有；Git 的其余动作走「跑完一次性返回」的执行路径，看不到中间过程，也停不下来。

我们决定：

- **主进程持有唯一的任务登记处**。各操作只往里报进度值（阶段、百分比、已完成字节、总字节）；速度与剩余时间由共享的计速器按「已完成字节」随时间的变化统一算，不用来源自报的速度。登记处节流后经一条通道推全量快照给渲染端。退出确认、Dock / 任务栏进度、顶栏任务清单都只读登记处。
- **会联网收发提交的 Git 动作改走流式执行**，命令加 `--progress`，进度解析由克隆专用扩展为 git 通用，各阶段按权重合成一个只增不减的总进度（权重同 IntelliJ）。
- **取消结束整棵进程树**：macOS / Linux 上 git 自成一个进程组、整组发 SIGTERM；Windows 结束进程树；WSL 照旧结束发行版里的进程组。git 会再起子进程（拉取的下载、推送前的钩子、子模块的克隆），只结束最外层的 git，它们会照样跑完。
- **拉取拆成两条命令**：先 `git fetch --progress <remote> <branch>`（可取消），再执行原有的 `git pull`（其中的获取已没有新内容，主要是合并或变基，不可取消）。Sourcetree 也是这样；IntelliJ 的「更新项目」、Tower、GitKraken 同样先获取再整合。
- **被隐藏的 Task 失败时不弹错误框**，失败留在任务清单、任务钮变红；找回时再在它所在的 Tab 里弹错误框。ADR-0052 里「后台操作的结果会弹在它所在的 Tab 里」对 Task 不再适用；不是 Task 的动作（如合并）隐藏后失败仍照 ADR-0052。

## Considered Options

- **主进程登记处（选中）**：退出确认与 Dock 进度本来就在主进程；渲染端重载后能接上已有的任务（与服务器传输同一做法）。
- **登记处放在渲染端**：任务的真实状态在主进程，渲染端只能从各条 IPC 拼出来；退出确认、Dock 进度还得再回传一次，渲染端重载即丢。
- **各操作照旧各自推进度，只统一界面组件**：速度、剩余时间、Dock 汇总、退出计数要在每个来源各写一份，正是现状的来路。
- **采用来源自报的速度**（git 输出里的吞吐量、electron-updater 的 `bytesPerSecond`）：不是每个来源都有（SFTP 只报字节），各来源平滑方式也不同，同一处界面会出现两种口径。
- **取消只结束最外层的 git**（VS Code 的做法，也是原先克隆的做法）：实测拉取的下载在叫停后又跑了约 40 秒并更新了远程分支，pre-push 钩子照样跑完，子模块的克隆又跑了约 44 秒、还在往目标目录里写。Sourcetree、Fork 都有用户报告关掉应用后 git 进程还在跑。
- **拉取：直接 `git pull`，按输出判断下载结束后再禁止取消**：`git pull` 的下载在 git 另起的子进程里，叫停外层进程停不掉它；下载结束的那一行与合并开始之间没有可靠的分界。
- **拉取：不能取消**：最简单，但拉取里最慢、最可能卡住的正是下载。
- **拉取：自己拆成获取 + 合并 / 变基，合并 / 变基也可取消，取消后 `git reset --merge` / `git rebase --abort`**（IntelliJ「更新项目」的做法）：要逐条复刻 `git pull` 的整合规则（配置、分叉点、squash 等），偏离原生行为；合并、变基是本机操作，通常很快，值不得为它接管整合。Fork 能在合并阶段取消拉取，有用户因此丢了本地改动。

## Consequences

- 拉取多一次与远程的连接：第二条命令里的获取只确认没有新内容。凭据走系统 credential helper / SSH agent，不会多问一次；需要每次连接都确认的密钥（如要触摸的硬件密钥）会确认两次。
- 先获取后的 `git pull` 与直接 `git pull` 结果相同：合并依据它自己写的 FETCH_HEAD；变基的分叉点依据远程跟踪分支的引用日志，先获取留下的那条记录也在其中。
- Git Task 没有总量与剩余时间：git 在下载完之前不知道包有多大。
- 退出应用时由登记处逐个取消进行中的 Task、结束各自的进程树（退出确认已提醒「中止这些任务」），不靠应用退出后管道断开顺带结束 git——钩子、子模块的克隆这类子进程不一定往管道里写，等不到这一下。
- 原先克隆的取消只结束最外层的 git，带子模块时会留下仍在写目标目录的子进程；改为结束进程树后，克隆的兜底清理才可靠。
- Windows 上结束进程不走 git 的信号清理，获取被叫停时可能留下临时包文件或引用锁文件（见 PRD「Further Notes」）。
- 服务器传输、压缩、数据源导出以后接入时，只需往登记处报进度值，不再各开通道。
