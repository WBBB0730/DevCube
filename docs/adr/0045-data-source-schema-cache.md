# 数据源的表结构存在磁盘上，显示即核对

目录若只在展开时读、每次展开都重新读（`docs/prd/database.md`「目录」），看到的永远是当前结构，但每连一次、每展开一层都要等「正在读取…」，云数据库上尤其明显；控制台的补全也要等列读完才能用。我们决定给登记的 **Data Source** 加一份表结构缓存，但它只用来「先显示」，每次显示都照样现查核对：

- **存什么**：只存结构——目录各层的节点、对象的定义或信息表、补全用的表结构（表与视图的列连同类型、库里的自定义函数与类型、外键，见 ADR-0047），只存读成功的；不存表数据，Redis 的键属于数据，也不存。每个 Data Source 一个 JSON 文件，放在 userData 下自己的目录里，带格式版本号，读不出、版本不对都按没有缓存处理；格式一改就升版本号，旧文件作废，下次连上重读；写盘防抖，先写临时文件再改名，退出时把待写的写完。
- **显示即核对**（stale-while-revalidate）：连上时读根、展开某一层、打开某个对象、控制台读补全，都是缓存与现查同时发出——有缓存就立即显示，现查到了原地替换并写回缓存；没有缓存时同原来。缓存从不单独作答，所以不会一直过时；别处改了结构（项目里跑了迁移、同事建了表），下一次显示就会跟上。现查读不出来时，目录与对象显示原因；补全与控制台的「库」「模式」留着缓存，有总比没有好。例外有两处。一是数据源上的配置对话框：它不依赖任何 Tab、自己没有连接，「库」的选项与补全直接用缓存，补全没有缓存时才借一个连着的 Data Source Tab 现查。二是目录的按名称筛选：它连同缓存里有、还没读取过的层一起找，这些层在筛选视图里直接用缓存显示，不为筛选现查；点开还没拿到的层时照常现查。
- **连上后分两批读完主体结构**：Data Source Tab 连上后，另开一条临时连接（不占 Tab 的连接）按对象类型批量读出目录写进缓存，分两批。只读显示的库（见下）。第一批为 PostgreSQL 一个库的各模式、各模式各分组的个数和表 / 视图 / 物化视图列表，MySQL / MariaDB 为显示的各库的各分组个数和表、视图，SQLite 为根的各分组个数和表、视图，读完即可用；第二批读同样这些模式或库里其余分组的对象——PostgreSQL 的函数、存储过程、序列、类型、触发器，MySQL / MariaDB 的存储过程、函数、触发器、事件，SQLite 的索引、触发器——另有 PostgreSQL 这个库的扩展与根下的角色、MySQL / MariaDB 根下的用户，内容同逐层读（函数带签名、触发器带所属表等）。补全用的全部列排在两批之间：它要的表与视图在第一批，不该被数量多的函数等拖慢。每写进一批、读取结束时推给这个 Tab，进行中的目录筛选随之更新；还在读时筛选没有匹配不算定论，显示「正在读取…」。之后展开这些层即从缓存显示、在后台核对；读完之前展开照旧逐层现查。
- **只读显示的库**：PostgreSQL、MySQL / MariaDB 的服务器上常有很多库，目录只列显示的库，后台也只读它们，同 DataGrip 的「N of M」、DBeaver 的「显示全部库」开关。显示的库由用户在目录根行勾选，按 Data Source 记在它的登记里（它的各个 Tab 一样），是用户的设置，不存进缓存。从没勾选过时只显示默认库：连接信息里填的库，PostgreSQL 没填时为连上后所在的库；MySQL / MariaDB 没填时一个都不显示，提示用户去勾选。连接信息被改时回到默认，根这一层不再列出的库（已删掉）从中去掉。PostgreSQL 一条连接只通一个库，显示的库一个库一条临时连接、同样两批，依次进行、不并发，连接所在的库显示时排在最前；MySQL / MariaDB 仍是一条连接一次读完。补全照旧只读连接所在的那一份，不因显示的库多读。勾上一个新库时，后台立即把它读一遍（正在读时排在最后）；取消勾选只是不显示、不再读，缓存留着。目录的按名称筛选只在显示的库里找，控制台的「库」也只列它们。
- **刷新时重跑**：手动刷新目录、或控制台执行了改结构或结束事务（COMMIT / END / ROLLBACK / ABORT）的语句后，两批都重跑（PostgreSQL 依次读各显示的库），没展开的缓存层也跟着更新；这时目录重读它涵盖的层要等读它那次读取的那一批，补全重读的列（控制台在连接所在的库上、这一次也读了补全时）要等它读的补全，都不另查。目录各层读到即换上，第一批的层与根不等第二批。补全跟着控制台上下文（ADR-0046）：PostgreSQL 按控制台所在的库各存一份，不写前缀的表补全到哪里直接取控制台上下文，控制台里 `use`、`set search_path` 之后跟着变。PostgreSQL 的缓存里存的「不写前缀时查找哪里」是新连接上的（数据源上的配置每次在新连接上跑，它的对话框直接用），不存控制台里改过的；MySQL / MariaDB 缓存里的这一项不用，对话框按填的库、控制台按控制台所在的库换掉。
- **失效**：编辑数据源、连接信息变了（与断开各 Tab 同一条路），或移除数据源时，删掉它的缓存；只改名、只改记住的密码不删。写回前核对读取时的会话还在，断开、重连之前发出的读取晚到时不写，旧结构不会写进新缓存。
- **范围**：只有登记的数据源的 Data Source Tab 读写磁盘上的缓存。Files 面板里直接打开的 SQLite 文件（不是 Data Source）不写盘：连上后同样分两批读完，读到的结构（目录各层、对象定义、补全）只放在这次会话的内存里，用法同缓存，关掉即丢。数据源上的配置的运行会话（ADR-0044）不用缓存。

## Considered Options

- **WebStorm 的做法：把结构存在磁盘上，打开时直接显示，不主动核对**：显示最快，但别处改了结构后，目录与补全仍是旧的，要手动刷新才跟上——这正是用户想摆脱的「改了表结构以后，目录和补全跟不上」。我们多付一次查询，换来每次显示都会被核对。
- **不缓存，每次现查**：永远是当前结构，也最简单，但每连一次、每展开一层都要等。
- **只缓存在内存里**：同一次运行里展开过的不再等，但重启之后第一次连接还是全都要等，而那正是等得最多的时候。
- **连表数据也缓存**：翻表也能先显示，但数据变得比结构勤得多，先显示旧行容易看错；数据也可能敏感，不该因为看过一眼就留在本机磁盘上。
- **连上时把所有库都读一遍**：筛选不用先展开就能找到任何库里的对象，但库多的服务器（如一个租户一个库）上读的大多是用不到的库，目录也被它们挤满；PostgreSQL 一个库要一条连接和两批查询，连一次就要开几十上百条连接、跑几百条查询，账号也可能连不上其中一些。所以只读显示的库，由用户勾选。
- **展开过的库记为用过、之后一直读**：不用另设开关，但只要展开过一次就一直读下去，用户看不到也改不了读了哪些；按缓存里有没有这个库的层推断更不可靠（控制台工具栏的列表也会把别的库的层读进缓存）。显示的库是明确的设置，看得到、随时能改。
- **显示的库存进表结构缓存**：跟着缓存走，不用另设字段；但它是用户的选择，不是读到的结构，缓存作废（改格式、删缓存）时不该丢。所以记在数据源的登记里，和名称、直连并列。
- **连上时只批量读表、视图与各分组的个数，其余分组展开时再读**：这次读取最快，但函数、触发器这类对象要展开读过一次才进缓存，目录按名称筛选在那之前找不到它们。DataGrip 也至少读出所有对象的名字与签名（它的第 1 级），所以连其余分组的对象（连同角色、扩展、用户）一起读；分成两批，表与视图那一批先读完、先可用，补全也排在它之后，都不被数量多的函数、触发器拖慢。

## Consequences

- 登记过的数据源的结构（表名、列名、视图与函数的定义）会留在本机磁盘上，移除数据源时才删掉；对象的信息表里偶有接近数据的内容（如序列的当前值），每次打开都会被现查替换。
- 缓存省的是等待，不是查询：每次显示照样查一次，连上时还多一条临时连接和两批批量查询。同一个数据源开着几个 Tab 时，各自连上各读一次，写进同一份缓存。
- PostgreSQL 每个显示的库再依次各多一条临时连接和两批查询：显示的库越多，后台读完所需的时间越长（控制台与表数据不受影响，只是筛选要等久一些才找全）。没显示的库里的对象筛选找不到，要先勾上。
- MySQL / MariaDB 没填默认库的数据源，第一次连上时目录里没有库，要先勾选；之后记在登记里，跨重启保留。
- 缓存没有淘汰：取消勾选的库的各层、打开过的对象定义会一直积累在这个数据源的文件里，直到连接信息被改或数据源被移除。
- 数据源上的配置对话框里的「库」选项与补全不核对：别处改了结构后可能是旧的，等某个 Data Source Tab 再读到、写回缓存才跟上。
- 刷新目录时，展开着的层要等这次批量读取把它所在的那一批读完才换上：第一批的层与根先换上，第二批的层（函数、触发器、角色等）要等补全与第二批都读完；PostgreSQL 排在后面的显示的库，其中展开着的层要等读到它那个库的那一批；刷新钮也转到那时，读取期间旧树照常显示。
- 目录筛选视图里从缓存取来的层不核对：别处删掉的对象（批量读取没覆盖到、也没有淘汰的层）可能仍被筛出，要展开读过一次才会更新。
- 批量读取在临时连接上进行，只看得到已提交的结构。PostgreSQL 与 SQLite 的改结构语句可以放在事务里，在控制台的事务里建了表、还没提交时，刷新后的目录与补全看不到它；所以结束事务的语句也触发重读，提交后自动再读一次就能看到。回滚到保存点、释放保存点不结束事务，不触发重读。
