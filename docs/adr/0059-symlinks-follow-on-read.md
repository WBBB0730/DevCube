# 符号链接：读时顺着链接，改时只动链接

各模块原本各自处理符号链接，口径互相矛盾：本机文件树不展开链接文件夹而服务器上的展开，筛选与 **Content Search** 跳过所有链接，监听拿 macOS 报回的真实路径去比登记路径，Git 的变更列表滤掉了类型变化（`T`）。范围见 `docs/prd/symlinks.md`。

我们决定全系统统一一条口径（VS Code、JetBrains、Zed 的共同做法）：**查看、打开、搜索、监听顺着链接到目标；删除、重命名、移动、复制、压缩只动链接本身。** 具体：

- 列目录只对链接多查一次目标，按目标类型显示；断链照常列出。
- rg 一律带 `--follow`（索引与搜索），并以 `--no-messages` 把读文件类错误与查询错误分开：前者不算失败。
- 监听订阅前取根的真实路径并把事件换回登记路径；经链接进到监听范围以外的、已列过的目录，另起一路递归监听，只驱动文件通道。
- Git 不另造链接语义：类型变化并入「修改」，链接文件不显示行号栏条纹。
- 服务器传输维持「文件链接传内容、文件夹里面的文件夹链接跳过」（同 WinSCP 默认），不随本机复制改成保留链接；直接选中的文件夹链接按目标传，上传、下载对称（同 FileZilla）。

## Considered Options

- **搜索不跟随**：快、无重复，但链接后面的内容永远搜不到，和树上看到的对不上。VS Code 与 JetBrains 都默认跟随，排除。
- **链接文件夹不监听、展开时重读**（VS Code 默认）：最简单，但展开期间看到的是旧内容；JetBrains、Zed 都跟随，选跟随，并只为已列过、且在监听范围以外的目录另起，数量随用户的展开而定。
- **类型变化单独一种状态**（VS Code、lazygit）：信息更准，但状态解析、图标、颜色、计数都要多一种；diff 已能看出类型变了，并入「修改」（JetBrains、GitHub Desktop）。
- **行号栏条纹按链接目标计算**（JetBrains）：要解析目标、判断它是否在仓库内再取它的基线，只有 JetBrains 这样做，不采用。
- **服务器传输按范围重建链接**（Cyberduck）：最周全但只有它这样做，实现也复杂；一律重建（Termius）会把指向范围外的链接带成断链。

## Consequences

- 指向项目内的链接会让同一文件在筛选与搜索结果里出现两次；指向巨大目录的链接会拖慢索引与搜索。
- 以后新增的 rg 调用要沿用 `--follow` + `--no-messages`，并按上面的规则判退出码 2。
- 以后新增的递归遍历（如「全部展开」这类自动展开）不能顺着链接走，否则循环链接会转不停；另起监听也跳过指向自己上级的链接。
- 路径上的「自身或在它里面」判断看不穿链接：移动、复制这类会落到别处的操作，还要按真实路径再判一次。
- 另起的链接监听活到项目监听或 Preview Window 的根监听释放为止，不随树上收起而撤销。
- WSL 里的目录不做监听的两项处理；列目录的效果未在 Windows 上实测。
